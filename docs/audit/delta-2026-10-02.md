## 1. Summary

Real progress. The previous audit's **Critical blocker is fixed** — subdivision codes are
now populated by migration, seed and script, so approval can mint establishment IDs.
**Phase E.1 schema landed** (table, enum, territory FKs, partial unique indexes, backfill),
**T.3 is built** (endpoint + `Suivi des retours` dashboard), and the **admin sign-out is
wired**. Build health holds: backend tsc clean, 828 tests passing, Prisma valid,
`next build` clean.

But the Phase E.1 integration is **incomplete in exactly the way the previous audit
predicted** (§4.6). `establishmentId` was repurposed in place from a company-code string
to an `Establishment.id` UUID FK, and **four queries that join it against
`Company.establishmentId` were not updated**. Both sides are `String`, so tsc passes and
tests pass; the failures are silent and runtime-only: campaign submission lists lose
company name and territory, **campaign reminder emails are never sent to anyone**, the
company dashboard reports every campaign as not-submitted, and one report buckets every
row to region "Inconnue".

Worse, two defects make Phase E's own purpose unreachable and risk the deploy:

- The live-return pre-check still filters on `companyId` while the DB index moved to
  `(establishmentId, quarterCode)` — so **a multi-site company cannot file a second
  site's return**, which is the entire point of Phase E (§3.2/N2).
- The Phase E.1 migration relinks only submissions whose company qualified for an
  establishment, then adds `NOT NULL` + FK unconditionally — so on real data containing a
  non-ACTIVE company, a null `companyId`, or a company missing territory, **the migration
  aborts** (§3.1/N1).

**Readiness: not deployable as-is.** N1 and N2 are release blockers; N3–N6 are silent
functional regressions against previously working behaviour. Of the previous audit's
findings, 6 are fixed and 9 remain open — including all of the Medium/Low hygiene items.

## 4. Defects, ranked

### Critical

**N1 — Phase E.1 migration aborts on real data (release blocker).**
`prisma/migrations/20261002180000_phase_e1_establishments/migration.sql:41-121`

Step 3 inserts establishments only for companies passing:
```sql
WHERE u.status = 'ACTIVE' AND c."establishmentId" IS NOT NULL
  AND c."regionId" IS NOT NULL AND c."departmentId" IS NOT NULL AND c."subdivisionId" IS NOT NULL;
```
Steps 4–5 relink submissions by `e."companyId" = s."companyId"`. Step 7 then applies
`SET NOT NULL` and the FK **unconditionally** (`:107-121`). There is no `RAISE`, assertion
or precondition check anywhere in the file.

Any of the following leaves a row that fails the FK and aborts the whole transactional
migration:
- a submission whose company's user is not `ACTIVE` (suspended, rejected, pending) — its
  `establishmentId` keeps the old company-code string;
- a submission with `companyId IS NULL` (the column was nullable at `5371722`) — Step 4
  cannot match it at all, and `SET NOT NULL` then fails;
- a company lacking `regionId`/`departmentId`/`subdivisionId` — including the ~29 companies
  the code itself notes as having no establishment ID
  (`src/auth/active-company.guard.ts:49`).

*Impact:* `prisma migrate deploy` fails and rolls back; the release cannot ship. Tests
cannot catch this because it depends on production data shape. **Not verifiable here — no
database access** — so this is a conditional finding, but the conditions are ordinary.
*Suggested fix:* before Step 7, either create establishments for every company with
submissions (relaxing the ACTIVE filter), or quarantine/relink unmatched rows explicitly,
and add a `DO $$ … RAISE EXCEPTION` precondition that fails with a readable message naming
the offending rows instead of a raw FK violation.

**N2 — Multi-site returns are blocked by the stale live-return pre-check (release blocker).**
`src/questionnaires/questionnaires.service.ts:1370-1377`

The DB index is now per `(establishmentId, quarterCode)` but the pre-check still filters
`companyId`. Site B's first return for a quarter is rejected with
*"Une déclaration est déjà en cours pour ce trimestre"* because site A already filed.
*Impact:* the one capability Phase E exists to deliver cannot be used; a multi-site company
is still limited to one return per quarter, now with a misleading error. *Suggested fix:*
filter on `establishmentId: resolvedEstablishmentId`, matching the index exactly.

### High

**N3 — Campaign submission list loses company name and territory.**
`src/campaign/campaign.service.ts:476-497` (join at `:481`, lookup at `:489`).
`companyName`, `region`, `department` are all `null` for every row. Silent — no error, no log.

**N4 — Campaign reminder emails are never sent.**
`src/campaign/campaign.service.ts:547-554` (join at `:552`). `_getPendingCompanies` returns
`[]`, so `sendReminders` (`:500`) has no recipients. The scheduler reports success having

exactly the direction nobody notices during a pilot.

**N5 — Company dashboard shows every campaign as not-submitted.**
`src/campaign/campaign.service.ts:592`. `getActiveCampaignsForCompany` filters
`CampaignSubmission` (UUID) by `company.establishmentId` (code), so the `submissions`
relation is always empty. Company-facing: a company that has filed is told it has not.

**N6 — Regional breakdown collapses to "Inconnue".**
`src/report/report.service.ts:853-857`. Every `campaignSubmission` row resolves no company,
so `region = 'Inconnue'` for all of them, making the report's regional distribution useless.

*Common fix for N3–N6:* resolve through the `establishment` relation
(`include: { establishment: { include: { company: … } } }`) rather than matching
`Company.establishmentId`. Each of the four is a two-line change; the risk is that they
were missed at all, which argues for renaming the column to `companyCode` (previous review
§3.1 option (c)) so the remaining mismatches become compile errors.
